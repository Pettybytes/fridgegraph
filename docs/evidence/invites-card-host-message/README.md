# Invitation card — readable layout with host and message (fixture proof)

Local fictional fixture proof, not a live Muse Image generation and not a served backend call. Every
capture comes from the standalone development page `/invites-preview.html`, which mounts
`InviteComposer` with `mode="mock"` and the fixed fictional sample art. No model, no invitation
record, no backend read.

Playwright (`web/e2e/invites-card.spec.ts`) ran in Chrome at **1440×1000** (project `desktop-1440`)
and **390×844** (project `mobile-390`). It clicked **Show sample invitation**, edited the occasion,
confirmed the canvas pixels changed while the art was fetched exactly once, captured light and dark
views, clicked **Download PNG**, and saved the downloaded file.

Both downloaded PNGs are byte-identical (SHA-256 `96b2ff7e8482cb039196fbdd9d3893b5555a95ed8f40ab12f4e1e2a35a4cad95`),
68135 bytes, PNG signature `89504e470d0a1a0a`, **1024×1024** — viewport width does not change the
exported card. I opened both exports and read them: the host line, child name, occasion, date, time,
place, the italic personal note and the `Sample art — not generated` footer all sit inside the art's
reserved quiet area with no clipping.

## What changed, and what each piece is for

| Piece | Job |
| --- | --- |
| Canvas (`Downloaded PNG · 1024 × 1024`) | Exactly the bytes **Download PNG** produces. Shown small because it is the artifact, not the thing you read. |
| Readout card under the canvas | The same lines at real type sizes (30px name, 18px occasion, 15px details, italic note), so the invitation stays legible at 390px where a 1024px square is scaled to ~350px. It is generated from the same ordered line spec as the canvas, so the two cannot disagree. |
| `Sample art — not generated` | Burned into the exported PNG footer *and* shown beside the preview, so the distinction survives a download, a screenshot, or someone reading only the image. |
| Source note | Names the provenance in plain words: a fixture in mock mode; in live mode, that live art generation is switched off and the fixture is being shown instead. |

The fixture art is unchanged: it is still the deterministic lavender placeholder generated by
`src/rosina/inviteFixture.ts`. It is not dressed up as a design, and it does not claim to be Muse
output.

## Visual review — three weakest things, and what I did

1. **The art is a flat placeholder, so the top two-thirds of the preview is empty.** I cannot replace
   it without a paid provider call or a backend fixture change, both out of scope. I labelled it
   explicitly instead of beautifying a placeholder, and added the host/message content so the card
   carries real invitation information rather than only a name and a date.
2. **At desktop size the burned-in canvas text is unreadable** (1024px art shown at ~370px). Fixed the
   legibility with the readout card at real type sizes, and fixed the ambiguity by captioning the
   canvas as the downloaded PNG rather than presenting it as the card.
3. **The default personal note is filler if a family never edits it.** It is a plain, honest line
   (`Please join us to celebrate!`) that is editable in one field, and it is never described as
   model-generated. A more specific default would have implied an event detail nobody supplied.

## Detector pass

**Source scan** (reviewing the invitation source) found one anti-pattern: a 3px
`border-left` accent on the provenance note — the recognisable single-side-colour tab of generated
UIs. Resolved in `invites.css`: the note now uses a full 1px hairline and a subtle `color-mix` tint
built from existing tokens, so the fixture state is carried by the text (which already said it
outright) plus a quiet surface change, with no side tab.

**Rendered scan** (reviewing the served invitation preview) reports one
finding: the cream page background `rgb(253, 250, 244)`. That colour is `--fg-canvas` in
`web/src/index.css` — the repo's shared warm-paper surface, fixed by `docs/contracts/design.md` §6
as the deliberate canvas for the whole product. The invites panel introduces no background of its
own, so this is a **justified waiver, not a change**: the CLI's only scoping option for this rule
is a file glob, which would also suppress a genuine cream misuse in this folder, so the reasoning
is recorded here rather than as a local detector suppression.

Both scans state their own limits: the source scan runs regex matching only, so the element rules
(tiny text, low contrast) do not run on files — those were checked in the real browser instead, at
1440 and 390, light and dark, by opening the captures linked above.
