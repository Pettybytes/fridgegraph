Everything below is observed in this repository on Oct 26, 2026, not copied from a tutorial.

## 1. Composition: seven owner subgraphs become one supergraph

Each subgraph owns its own types and writes only its own tables (`src/subgraphs/*.ts`).
Federation lets one type be *assembled* from several subgraphs without any of them owning it whole.

**Entities are the seam.** `village` declares the spine:

```graphql
type Person  @key(fields: "id") { id: ID!  displayName: String!  birthDate: String! ... }
type Child   @key(fields: "id") { id: ID!  person: Person }
type Household @key(fields: "id") { id: ID!  village: Village }
type Group   @key(fields: "id") { id: ID!  name: String!  kind: String! }
```

The other six declare **stubs** — the key, and nothing else:

```graphql
# access, coordination, schedule, school, transport, activities
type Person @key(fields: "id") { id: ID! }
type Child  @key(fields: "id") { id: ID! }
```

A stub is a promise: "I can be handed a `Person` by id, and I contribute no fields to it."
Because every stub declares only `id`, no two subgraphs can disagree about a shared field, so
composition has nothing to resolve. `transport` is the one subgraph that adds a field to someone
else's entity — `Person.vehicles` — which is legal because village never declares that field.

**How composition happens locally.** `supergraph.yaml` names seven `subgraph_url`s;
`rover dev` introspects each running subgraph every second, feeds the SDL to the Federation 2.9.0
composer, and hot-reloads the router when a schema changes. Nothing is published to GraphOS for
the local loop.

**What composition does *not* check.** It verifies the schemas agree. It does not verify that any
resolver enforces anything — see section 3.

Evidence that it really assembled: `supergraph.graphql` (422 lines, generated by
`rover supergraph compose`), and the fact that one operation below touches four services.

## 2. Query planning: what the router did for evidence #1

Evidence #1 asks for the child, today's events, today's practices, `approverFor`, and
`pickupCandidates` with contacts and vehicles. The router split that single document into this
plan (verbatim traversal of `extensions.apolloQueryPlan`, saved in
`docs/evidence/01c-query-plan-full.md`):

```
Parallel
 Fetch → village
 Fetch → schedule
 Sequence
  Fetch → activities
  Flatten [practices.@.group]
  Fetch → village
 Sequence
  Fetch → access
  Parallel
   Flatten [pickupCandidates.@.person]
   Fetch → village
   Flatten [pickupCandidates.@.person]
   Fetch → transport
   Flatten [approverFor.fyiParents.@]
   Fetch → village
   Flatten [approverFor.approver]
   Fetch → village
```

Reading it:

- **`Parallel` at the root** — `child`, `events`, and the practices/candidates branches have no
  data dependency on each other, so the router issues them concurrently. Three round trips start
  at t=0, not three sequential waits.
- **`Sequence` inside a branch** — `practices` returns a `Group` reference; the group's `name` lives
  in `village`, so that fetch cannot start until `activities` has answered. Same shape for
  `pickupCandidates`: `access` decides *who* the candidates are, and only then can `village` resolve
  their names/contacts and `transport` their vehicles.
- **`Flatten`** is the fan-out point. The router collects the entity references from the list
  (`pickupCandidates.@.person`) and sends **one** `_entities` request with a representations array,
  rather than one request per person. Two `Flatten → village` fetches appear for
  `pickupCandidates` because the planner batches them by selection set; the practical point is that
  the candidate count does not change the number of requests.
- **Four services for one document** (village, schedule, activities, access, transport — village
  twice as a data source and twice as an entity owner). The mobile client asks one question.

That plan is also why `access` must be cheap: it is the gate that the village/transport entity
fetches hang off.

## 3. Runtime authorization: a composed schema is not a permission

Composition answers *"what may be asked?"*. It never answers *"may this caller see it?"* — there is
no place in a supervisor SDL to express "this field, for this child, by this person, until Nov 30".

So every resolver calls into `src/authz.ts` before returning anything:

| Function | Meaning |
| --- | --- |
| `requireCaller` | unknown/missing caller → `UNAUTHORIZED` |
| `isParentOf` | caller is a `HouseholdMember` with role `parent` in one of the child's households |
| `hasScope` | a grant for this child carries the exact scope, **valid on the requested date** |
| `authorizeChild` | parent ⇒ full access; otherwise the exact field scope is required |

Denials are raised as a GraphQL error with `extensions.code = "UNAUTHORIZED"` and the field is
`null` (`deny()` in `src/authz.ts`). A caller who is authorized but has nothing to show gets `[]`
instead — the two are deliberately different, because "you may not ask" and "nobody is cleared for
pickup" are different facts (see `docs/evidence/05a`, `05c`).

Two consequences worth stating plainly:

1. **The router is not a security boundary here.** `router.yaml` propagates `x-demo-user` and
   `x-demo-date`; it does not evaluate them. All authorization happens in the subgraphs, which is
   where the data is.
2. **The identity in these headers is not verified.** Any client that can reach port 4010 can claim
   to be any parent. The *rules* are real and enforced per resolver; the *caller* is not yet
   authenticated. Real JWTs arrive in Milestone 2.

The UNAUTHORIZED evidence, if you want to see the rules bite:
`04` (grandmother denied the medical file), `05a`/`05b` (schedule-only grantees denied the candidate
list), `06b` (time-boxed grant expired by one day), `07b`/`07c` (bus driver: roster yes, schedule and
care plan no), `10a`–`10d` (cross-village denial).

## 4. Verified identity replaced the demo headers

Milestone 1 trusted `x-demo-user`. Milestone 2A trusts a **Supabase-issued JWT** and nothing else.

**Where it is checked.** In `src/auth/verify.ts`, called from `src/context.ts` for every request:

| Step | Rule |
| --- | --- |
| Header | must match `Authorization: Bearer <token>`; otherwise `missing`/`malformed` |
| Signature | `createRemoteJWKSet` against `<project>/auth/v1/.well-known/jwks.json` |
| Algorithm | **ES256 only.** A token offering `alg: none` or `HS256` never reaches signature work |
| Issuer | exactly `<project>/auth/v1` |
| Audience | exactly `authenticated` |
| Claims | `sub`, `exp`, `iss`, `aud` all required; 5s clock tolerance |
| Identity | map[`sub`] → fixture person via `data/identity-map.json`; unmapped ⇒ rejected |

**Why in the subgraphs and not only at the router.** Two reasons, both concrete:

1. `authentication.router` (router-level JWKS validation) is **licence-gated**: unlicensed/offline
   the router exits at startup with *"Not connected to GraphOS … license for: Authentication
   plugin"*. Connected with `APOLLO_KEY` + `APOLLO_GRAPH_REF`, the same configuration starts, logs
   `UpdateLicense(Licensed)`, and rejects bad tokens at the edge (evidence `15`). Even then it is not
   the boundary: a *missing* token is not stopped at the edge (documented), so only the subgraph
   check covers every path.
2. Each subgraph port is independently reachable on `127.0.0.1`. An edge-only check would be
   bypassable by anyone who can reach 4001–4007 directly. Verifying where the data lives is the
   only check that cannot be routed around.

**Two failure codes, deliberately different.** `UNAUTHENTICATED` = "I do not know who you are"
(absent, expired, bad signature, wrong issuer/audience, unmapped `sub`). `UNAUTHORIZED` = "I know
exactly who you are, and you lack this scope for this child." Milestone 1's scope assertions still
expect `UNAUTHORIZED`, so collapsing the two would silently weaken them — evidence `14a`/`14b`
pin the other side.

**The one surviving header.** `x-demo-date` is a test clock and is honoured **only** when the server
runs with `DEMO_CLOCK=1`. Verified both ways: with the clock off, a client sending `2026-10-27`
still resolves Daniel's one-day grant for the 26th (header ignored); with `DEMO_CLOCK=1` the same
request correctly denies. This exists because the whole demo lives on a fixed Monday, not because
clients should ever set the date.

**A bug this surfaced.** `today` was computed with `toISOString()` — UTC — so at 20:00 Detroit time
the "day" flipped to tomorrow and a grant valid for the whole local day silently expired. Household
calendars are local date ranges (grants, `ParentingSchedule`, policies), so `today` is now computed
in `APP_TIME_ZONE` (default `America/Detroit`). Milestone 1 never saw it because every test passed
an explicit date.

**MCP.** The pinned `headers:` block is gone. `forward_headers: [authorization]` passes the caller's
token through to the router, and the subgraphs verify it as usual; a tokenless MCP call now returns
`UNAUTHENTICATED` inside the tool result. Apollo MCP Server logs a warning when forwarding
`Authorization` — expected, since the router/subgraphs are the validators, not the MCP server.
