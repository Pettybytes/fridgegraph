# Village pulse read inventory — before implementation

All graph reads use the signed-in perspective's in-memory bearer through the existing Apollo client and `runRead`. `coordinationJobs(childId)` is filtered by the caller's database RLS; `attempts(jobId)` is RLS filtered; `jobTimeline(jobId)` returns no entries for an invisible job. `orbitStatus(childId)` is likewise caller scoped and returns the latest visible alert's safe status fields. The UI must refuse non-parent perspectives rather than treat an authorization failure as an empty village. No shared stack was queried for this inventory.

| Proposed panel | Existing read and fields | Window and calculation | Decision |
| --- | --- | --- | --- |
| Coverage / recent requests | `coordinationJobs` gives `id`, `status`, `idempotencyKey`, evaluations and confirmation; `jobTimeline` gives `JOB_CREATED` time. Calendar reads do not link a care requirement, its needed coverage period, and a completed outcome to a job. The key is not a public request-date field. | No defensible covered/pending/uncovered denominator or upcoming-request date exists. Show caller-visible requests **created** in the displayed Detroit date window with their recorded statuses. Do not classify a calendar gap, silence or absent confirmation as uncovered. | **Recent pickup requests** compact dated list only; no coverage percentage or classification. |
| Recorded request counts | `coordinationJobs(childId)` IDs, `type`, current status and confirmation; `attempts(jobId)` IDs and attempt `at`; `jobTimeline(jobId)` has `JOB_CREATED` at. The existing job query is extended to select the already-defined `type` field. | Cohort: distinct visible **PICKUP** jobs with a recorded `JOB_CREATED` on the last 30 Detroit calendar dates, inclusive. Count distinct jobs in the cohort; then independently count jobs with at least one recorded contact attempt and jobs with a recorded parent-approval confirmation. The attempt timestamp proves an attempt was recorded, not delivery or response. These are job counts, not attempt counts or verified pickups. Jobs without creation time cannot enter this dated cohort. | Three independent horizontal bars, not conversion stages. |
| Response time | `attempts` exposes attempt `at`, `closedAt`, `closedReason`; evaluations expose `acceptedVia` but no reply instant. `jobTimeline` has attempt opened/closed and parent `CONFIRMATION`, but no caregiver response event. | A duration requires an attempt/contact instant and the matching actual caregiver response time. Attempt closure or timeout is not a response. No sample size or duration can be calculated. | **Omitted** from the pulse; read gap explained in the accessible calculation disclosure and [proposed data contract](../../../docs/contracts/village-pulse-data.md). |
| Open items | Jobs expose current `status`; `awaiting_approval` is explicitly waiting on a parent under `docs/contracts/pickup-job.md`. The Orbit controller's existing `orbitStatus` read exposes `alertId` and `status` for the **latest visible** alert. The controller can retain a cached status while a refresh puts an error in `state.error` without changing `phase`. | Current caller-visible items, not a historical window. Show a count tile for pending-approval jobs and a 0/1 tile for the latest visible active Orbit status. Error/refusal takes precedence over cached status, leaving no current count. Link to Mission Control and Orbit only on ready reads. No alert message, photo, place, descriptors or controls. A null latest status cannot prove that no older active alert exists. | Supported with the latest-alert limit stated and a failed/refused read state. |

The dates and cohort are displayed in `America/Detroit`. A stored demo record is labelled as such. Each panel has its own loading, empty, refused and failed handling; an unavailable measure is never rendered as zero. Detailed limits are also in the accessible “How this is calculated” disclosure.
